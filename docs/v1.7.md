## Overview

Facon 1.7 "Filo" gains approximately **+130 Elo** over 1.6 "Temple" (~2930 vs ~2800 Ordo). In self-play at 10+0.1 it measured **+139.1 Elo over 1.6** (n=10000).

Where 1.6 was an evaluation overhaul and 1.5 was dominated by one bug fix, 1.7 splits almost evenly between search and evaluation, and no single change dominates. The search gained a family of history tables, a static evaluation that is always available and cached in the transposition table, singular extensions, ProbCut, and a pawn-structure cache. The evaluation gained threat terms broken down by attacker and victim -- the largest single feature of the cycle -- plus endgame scaling that resolves a limitation carried since 1.5, and a re-fitted weight set.

The methodology was the same as 1.6, tightened: every feature was added alone, measured in self-play against the previous accepted build, and kept only if it measured positive. Because summing individual gains overstates the total, two long checkpoint matches against 1.6 were run mid-cycle to keep the accumulated figure honest. The first showed the naive sum was, if anything, slightly conservative over three features; the second showed it running about 8% long over six. That 8% discount was applied to projections thereafter.

## Search: the History Family

**Two-sided history.** The butterfly table `history_[color][from][to]` previously received only a bonus, on the quiet move that caused a beta cutoff. It now also applies the symmetric penalty to every quiet move searched before it at that node -- moves that had their chance and failed. Both updates use the gravity form

    entry += delta - entry * delta / HISTORY_MAX

which pulls entries toward the `+/-HISTORY_MAX` asymptote in proportion to how far they already are, so values decay as new evidence accumulates instead of saturating into indistinguishable clamps. `delta` is `min(depth^2, HISTORY_MAX)` and the multiplication runs in 64-bit, since `entry * delta` does not fit in 32.

Moves searched but not cut are remembered per node in a fixed array capped at 64 entries: past the first 64 quiet moves the ordering signal no longer distinguishes anything, and the cap bounds the per-frame stack cost.

**Continuation history.** A second table, `conthist_[prev_piece][prev_to][piece][to]` (about 3.5 MB, static storage), conditioned on the opponent's previous move. Where the butterfly table asks how good a move has been in general, this asks how good it has been *as a reply to that specific move* -- the generalization of the countermove heuristic, which remembers only one refutation per opponent move. The row for the node's previous move is computed once per node, next to the countermove lookup, and threaded down to move scoring.

Unlike the butterfly table it is **reset per game rather than per search** (`Search::new_game()`, called from `ucinewgame`): clearing 3.5 MB on every search would cost roughly half a millisecond per move, and the signal learned earlier in a game is exactly what later moves want.

**Move ordering.** Quiet moves are scored `HISTORY_MAX/2 + (butterfly + continuation)/4`, a mapping chosen so the two-sided range compresses back into the same band single-sided history occupied. Every other ordering tier -- transposition move, good captures, killers, countermove, bad captures -- keeps its previous bounds untouched.

## Search: the Static Evaluation Channel

**Entry layout.** `TTEntry` remains exactly 16 bytes, now enforced by `static_assert`:

    hash (8) + move16 (2) + score (2) + eval (2) + depth (1) + gen_bound (1)

The move shrank to 16 bits because the engine's move encoding uses exactly bits 0..15 (`from | to<<6 | type<<12 | promo<<14`), so the truncation is lossless and an accessor restores the full move. The two freed bytes hold the node's static evaluation, with a sentinel recorded for nodes in check. Entries per megabyte are unchanged.

**Pipeline.** Every node outside check evaluates exactly once, in this source order: the entry's `eval` field when present; `evaluate()` otherwise; then refinement by a usable stored score bound (a lower bound above the evaluation raises it, an upper bound below it lowers it -- the search knew better than the bare evaluation). The result feeds reverse futility, razoring and move-level futility, is pushed to a per-ply stack, and is stored back with this node's entry.

**Three channels, kept apart.** This is the correctness story of the block. The *raw* evaluation is the only thing written back to the transposition table; the *working* value is raw plus the learned correction plus any bound refinement, and is what the search uses; the *searched score* has its own field entirely. Storing anything but the raw channel compounds on every revisit.

**Improving.** `!in_check && ply >= 2 && eval_stack_[ply-2] != NONE && static_eval > eval_stack_[ply-2]`, with a conservative false whenever either node was in check. Three consumers, in deliberately opposite directions: the reverse-futility margin *shrinks* when improving (above beta and rising, the fail-high is trustworthy), the move-level futility margin *grows* (below alpha but rising, quiet moves may still recover), and the late-move-pruning threshold tightens to two thirds when *not* improving (a stalled position promises less from late moves).

## Search: Singular Extensions

When the transposition table already knows a node's best move to serious depth with a usable bound, the node re-searches **itself** -- same ply, same board, the call deliberately not negated -- with that move excluded, at `(depth-1)/2`, against a null window `SE_MARGIN * depth` below the stored score. A fail-low proves the move singular and it searches one ply deeper.

The exclusion is threaded through a per-ply array rather than a function parameter, so no signature changed. Three guards keep the verification from seeing or touching the entry it is questioning:

1. the transposition cutoff is skipped while an exclusion is active -- otherwise the verification would answer with the very entry under test;
2. **both** store sites are barred -- a world without the best move must not pollute the real entry;
3. the move loop skips the excluded move **before** the legality check and the legal count.

The third guard buys a property for free: an only-move node sees zero legal moves, returns a mate or stalemate score, fails the verification low, and is therefore correctly singular.

The block sits after all early-return pruning, so a node that reverse futility, razoring or null-move pruning resolves never pays for a verification.

## Search: ProbCut

The capture-side counterpart to null-move pruning. At non-principal-variation nodes of sufficient depth, sound captures (those that do not lose material on the exchange) are searched at `depth - 4` against a null window set `PC_MARGIN` above beta; the first one to reach that raised target returns immediately and the cutoff is stored as a lower bound at `depth - 3`.

Two cheap gates keep hopeless nodes from paying for it: the static evaluation must be plausibly close to beta or above, and a deep-enough transposition entry whose score already sits below the target vetoes the attempt outright. Candidates are ordered by the same machinery quiescence uses, and the excluded move of an active singular verification is invisible here too.

This is the one feature of the cycle whose verdict required two runs: the first returned a clear negative, the second a clear positive, and a pooled estimate over 17,000 games settled it as slightly positive. It costs no measurable speed and shrinks the tree by about 18% at depth 18 while costing 6% at depth 8, so it stayed.

## Speed: the Pawn Key and Pawn Cache

`Board` maintains a second Zobrist key covering **pawn placement only** -- no side to move, no castling rights, no en passant -- updated incrementally by the same three helpers that maintain the main position key, gated on the moved piece being a pawn. `StateInfo` saves and restores it alongside the main key.

The pawn-structure part of the evaluation is a pure function of that configuration: it reads exactly two things from the board, the two pawn bitboards, and returns raw middlegame and endgame poles -- the tapered blend lives in `evaluate()`, so not even the game phase can change its result. The passed-pawn refinements that do read kings and blockading pieces live in a different function. Its output therefore depends on pawn placement alone, and the function is split into a pure computation and a caching wrapper keyed by the pawn key (2^14 entries, about 192 KB).

Entries self-invalidate on a full 64-bit key comparison, so there is no clear operation: nothing in a running engine can change what a given pawn structure evaluates to. The empty-slot sentinel is key 0, which is also the true key of a pawnless position; that collision is exact rather than lucky, since with both pawn bitboards empty every term iterates zero times and the computation returns zero.

Correctness here was verified two ways. The cached values are identical to the computed ones by construction, so the **benchmark signature must not move** -- and it did not, at either depth. Separately, a harness walked 13.4 million positions across five starting points comparing the incremental key against a from-scratch recomputation, and checking that unmake restores it exactly, with zero failures.

## Evaluation: Threats

Six families, counted by **attacker type and victim class** rather than collapsed into one generic term, because they mean different things: a pawn hitting a knight usually wins material or a tempo outright, a rook hitting a queen mostly gains time, and a piece attacked without being defended is a different kind of problem from one merely attacked.

| Term | Counts |
|------|--------|
| pawn on minor | enemy knights and bishops attacked by our pawns |
| pawn on major | enemy rooks and queens attacked by our pawns |
| minor on major | enemy rooks and queens attacked by our minors |
| rook on queen | enemy queens attacked by our rooks |
| hanging | enemy minors and majors we attack and they do not defend |
| pawn push | safe single pawn advances that would create a threat |

All counted from White's perspective as (white - black), each with its own tapered weight pair.

**Where the attack maps come from** is the implementation's whole point. The mobility calculation already generates every piece's attack set and discards it. The maps are therefore accumulated *there* -- once in the evaluation and once in the parallel walk that produces the linear decomposition -- and handed to a single shared counting function. A standalone second sweep was implemented first and measured about 10% of search speed; folding into the existing sweep keeps the same six terms for about half a percent. Only the accumulation lines are duplicated across the two paths, exactly as the mobility counts themselves already are; every decision about which bitboard intersects which lives in one place, and the `trace` command's fidelity check verifies the two paths still agree.

## Evaluation: Endgame Scaling

The final score is multiplied by a factor chosen from the material signature, after mopup and before the side-to-move flip, with the strong side read off the sign of the score exactly as mopup picks it.

| Signature | Factor | Effect |
|-----------|-------:|--------|
| the strong side cannot force mate | 4/128 | K+B vs K: about +330 becomes about +10 |
| rook against a single minor, no pawns | 32/128 | drawn with correct defence, won often enough in practice |
| opposite-coloured bishops, no other pieces, pawn difference <= 1 | 48/128 | the classic drawn-but-not-dead ending |
| everything else | 128/128 | untouched |

**None of the factors is zero, deliberately.** An outright override to zero was attempted in 1.5 and reverted after measuring about a 30 Elo regression. The likeliest reason is loss of gradient: with an exact zero the engine cannot tell "keep the bishop" from "give the bishop away" -- both evaluate identically -- so it will shed material for nothing, and the evaluation jumps discontinuously the moment the last pawn comes off. A small non-zero factor says "this is a draw" just as clearly, far below anything that would make the engine decline a draw, while preserving that ordering.

Combinations that genuinely win are untouched: two bishops of **opposite** colours, bishop and knight, rook or queen against a lone king. The definition of insufficient mating material is now a single function shared by the mopup guard, the scaling, and the verbose evaluation display, where it previously existed in three copies.

The factor is recorded in the evaluation trace and re-applied when reconstructing the score, so the bit-exact contract between the two evaluation paths holds without giving the reconstruction function a board.

## Evaluation: the Re-fitted Weight Set

After the threat terms were added with hand-chosen starting values, all 946 weights were re-optimized against a corpus of 7.15 million labelled positions. The result is instructive about where the correction was actually needed:

- The **twelve threat weights** moved by an average of 24.5 points, with a maximum of 58.
- The **other 934** moved by an average of 3.5.

And the threat weights moved *coherently*: five of six middlegame values up, by factors of 1.75 to 5; five of six endgame values down, two crossing to zero or negative. That matches what a threat is worth in each phase -- a threat is paid for in tempo, which is worth much more with the board full than in a simplified ending. The one term left almost untouched was "hanging", which is about material rather than tempo and is correspondingly phase-neutral.

Outside the threat group, the largest movements were in the knight outpost terms and the knight and bishop piece-square tables -- the pieces most involved as attackers and victims of the new terms, redistributing value rather than inventing it.

The overall error fell by only 0.27% and plateaued from the hundredth epoch onward, so the fit's objective and playing strength are clearly not the same quantity. The change nonetheless measured about +6 Elo in self-play.

## Features Attempted and Rejected

- **Capture history**: roughly neutral over 16,250 games, slightly negative at the end. The existing capture ordering -- most-valuable-victim ordering split by static exchange evaluation, with a shortcut for obviously favourable captures -- was apparently already good enough that a learned refinement had nothing to add.
- **History pruning**: killed at the design stage by instrumentation, before any games were played. With the butterfly table resetting per search, `depth^2` deltas and efficient ordering, genuinely bad quiet moves are rarely searched and failed -- the cutoff arrives first -- so the penalty lands mostly on good-but-not-best moves searched just before the one that cut. A margin sweep confirmed it: wide margins never fired at all, narrow margins fired and made the tree **grow**, and only an essentially-zero margin pruned, indiscriminately. The two-sided signal is excellent for relative ordering and unsuitable as an absolute threshold.
- **Principal variation search**, textbook ladder: negative. The intermediate full-depth null-window verification between the reduced probe and its resolution is a compounding tax on the principal-variation spine -- the tree shrank 14.6% at depth 8 but **grew** 12.7% at depth 18.
- **Principal variation search**, restricted form: recovered about two thirds of the loss but stayed negative. The residue points at something deeper than node counts: before the change every child of a principal-variation node received a full window, so the variation was a wide tree of exact scores feeding the transposition table. Scouting narrows it to a spine of bounds, and the lost information -- worse entries, worse ordering, less stable aspiration -- costs more than the saved nodes return.
- **Correction history**: learning where the static evaluation is systematically wrong, indexed by pawn structure. Its expected range was ruled out early and it never separated from zero.

## Bench Results

    depth  8:     498,639 nodes
    depth 18: 241,031,431 nodes

Two notes on these numbers. The depth-8 signature is shared with the pre-scaling build because none of the ten benchmark positions reaches a drawish material signature that shallow; the depth-18 number moves because the search does reach them inside the tree. And the pawn cache deliberately did **not** move either number when it was added: a pure cache in front of a pure function must not, and that invariance is what proved it correct.

Benchmark positions and depths are unchanged from 1.6.

## Gauntlet Results

Gauntlet 4 -- the same high-Ordo field 1.6 was measured against (26 opponents averaging ~2677, range ~2500-2814, 2min+1sec, 40 games each): **829.0/1040 (79.7%)**. Combined Ordo across all Facon versions and the gauntlet field rounds to **~2930** (n=1040 for 1.7). This places 1.7 first in the combined list, above every engine in the field; the strongest of them, Glaurung 2.2, rates ~2814.

Because 1.6 and 1.7 played the identical 26 opponents, the comparison needs no calibration between fields: from 65.1% to 79.7% against the same opposition, a gain of about **+130 Elo** in the field. Direct self-play vs 1.6 measured **+139.1 Elo** (n=10000, +/- 5.4) at 10+0.1, in close agreement.

Gauntlet 5, against a stronger field (average ~2970, the strongest at ~3108), is being run with a balanced opening book; its results will be added to the gauntlet results document when complete.

## Known Limitations

- **No endgame tablebase support.** Endgame scaling recognizes material signatures but does not know exact results; positions that are theoretically won or drawn for non-material reasons are still evaluated heuristically. Tablebase probing is planned for a future version.
- **Single-threaded search.** The engine uses one search thread regardless of the hardware available. Parallel search is planned for a future version.
- **No opening book.** Play from the initial position relies entirely on search and evaluation.
